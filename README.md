# DYHOUSE · Parcerias imobiliárias

**[Abrir o site público](https://deyvidybraz.github.io/dyhouse-parcerias/)** · **[Arquivos de pesquisa](https://github.com/DeyvidyBraz/dyhouse-parcerias/tree/main/dist/dados)** · **[Modelo de novo lote](exemplos/novo-lote.exemplo.json)**

Página HTML para explorar pesquisas, acrescentar novos lotes JSON e acompanhar o contato de parceria de cada empreendimento. A base reúne **198 empreendimentos**, incluindo **118 na Zona Sul de São Paulo capital**. São 159 na capital e **39 em Alphaville/Barueri**. A expansão de 02/11/2026 acrescenta 59 produtos à base anterior de 139. A importação consolida registros repetidos, mantém as fontes e expõe divergências para revisão.

Os filtros incluem empresa, **cidade**, região, bairro, tipo, MCMV, estágio, ano e **status da sua parceria**. Alphaville aparece como localização/bairro; os municípios da nova pesquisa são **Barueri (35)** e **Santana de Parnaíba (4)**.

## Acrescentar arquivos pelo GitHub

1. Abra a pasta **[dist/dados/](https://github.com/DeyvidyBraz/dyhouse-parcerias/tree/main/dist/dados)** no repositório.
2. Clique em **Add file → Upload files**, escolha os novos arquivos `.json` e confirme **Commit changes** na branch **main**. Quem não tem permissão de escrita pode propor uma alteração por pull request; ela só entra no site depois de aprovada e incorporada a `main`.
3. Aguarde a publicação terminar na aba **[Actions](https://github.com/DeyvidyBraz/dyhouse-parcerias/actions)**. O GitHub pode levar alguns minutos para disponibilizar a atualização.
4. Abra o site e clique em **Atualizar**. O novo lote entra na leitura; a consolidação de empreendimentos repetidos e os filtros são recalculados.

**Não é necessário editar uma lista de arquivos.** O GitHub Pages recria `dist/datasets.manifest.json` automaticamente a cada publicação, enumerando os JSON da pasta `dist/dados/` e de suas subpastas. Esse arquivo no código-fonte é um template; no site publicado ele vira JSON válido. Cada lote precisa ser JSON UTF-8 puro, sem cabeçalho YAML. Use nomes como `lote-novembro.json`, evitando arquivos e pastas iniciados por `.`, `_` ou `#`, que o Jekyll pode ignorar.

O arquivo de exemplo contém nomes fictícios e fica fora da pasta publicada de pesquisas. Substitua os exemplos por dados reais antes de enviar um lote. Arquivos inválidos geram aviso na interface e não entram na contagem.

**Código e pesquisas deste repositório são públicos.** A pasta de pesquisas recebe somente informações destinadas à publicação. Os status e a linha do tempo do seu contato ficam no navegador ou no JSON de acompanhamento que você escolher; o painel não os envia para este repositório. Para compartilhar a base de pesquisa com alguém, basta enviar o link do site. Cada pessoa mantém seu próprio acompanhamento.

### Configuração do GitHub Pages

Em **Settings → Pages**, a origem é **Deploy from a branch → main → / (root)**. O índice da raiz abre o painel em `/dist/`, com caminhos relativos que funcionam no endereço de projeto do GitHub.

O catálogo usa o Jekyll nativo do Pages, sem dependências de execução no navegador nem token de acesso. Não adicione `.nojekyll`, pois isso desativa a geração do catálogo. A publicação é acionada por commits normais em `main`; segundo a documentação do GitHub, commits enviados por Actions com `GITHUB_TOKEN` não acionam esse build por branch. O GitHub ainda executa seu workflow de Pages para publicar.

Referências: [origem e atualização do Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [arquivos estáticos do Jekyll](https://jekyllrb.com/docs/static-files/).

## Status e linha do tempo do contato

Abra **Ver detalhes** em um empreendimento para acessar o acompanhamento. Escolha **Não solicitada**, **Parceria solicitada** ou **Parceria feita**. No campo de texto, descreva o contato e clique em **Registrar progresso**. Cada registro mantém data e hora; mudanças de status também entram na linha do tempo. As marcações representam o que você registrou, sem enviar solicitações às empresas.

O histórico fica ligado à identidade do empreendimento, não à posição na lista. Atualizações, filtros, novas pesquisas e consolidação de duplicatas preservam o acompanhamento. Cidades e fases distintas continuam separadas. As anotações são exibidas como texto, incluindo quebras de linha; texto importado não é executado como HTML.

### Onde o acompanhamento fica salvo

| Modo de uso | Gravação |
|---|---|
| **Pacote com servidor local** | Automática em `acompanhamento/parcerias-acompanhamento.json`, fora da pasta de pesquisas. O arquivo anterior fica em `.json.bak`. |
| **Site online ou HTML avulso, com navegador compatível** | **Vincular arquivo JSON** permite escolher um arquivo e autorizar gravação. A página salva as alterações no arquivo enquanto ele está vinculado. **Abrir acompanhamento** permite continuar a partir de um JSON existente. |
| **Navegador sem gravação direta de arquivos** | As marcações e notas ficam no armazenamento local do navegador. Use **Backup JSON** para baixar uma cópia e **Abrir acompanhamento** para restaurá-la. |

O indicador **Seu acompanhamento** informa se a gravação ocorreu no arquivo ou somente no navegador, e mostra falhas de salvamento. Depois de reabrir o HTML/site, pode ser necessário selecionar o arquivo novamente: o vínculo de escrita não é mantido silenciosamente entre sessões. O modo local com servidor retoma o arquivo automaticamente.

**O HTML não reescreve a si mesmo.** A solução de arquivo é um JSON de acompanhamento reutilizável, com todos os status e eventos. Isso permite atualizar o site ou os arquivos de pesquisa sem sobrescrever seu trabalho. A exportação **Exportar → JSON** também leva os dados dos empreendimentos e o acompanhamento correspondente ao recorte. Para guardar todas as marcações, inclusive de produtos fora do filtro atual, use **Backup JSON**.

As marcações não são sincronizadas automaticamente entre dispositivos ou navegadores. Leve o JSON de acompanhamento para continuar em outro dispositivo. A importação combina históricos e preserva eventos; a mudança de status mais recente prevalece. Use uma janela por vez para gravar no mesmo arquivo vinculado em navegadores ou sessões diferentes. No servidor local, revisões concorrentes são detectadas e conciliadas. Antes de trocar de computador ou limpar os dados do navegador, gere o backup.

No pacote local, a pasta `acompanhamento/` não é servida como arquivo público e está excluída do controle de versão. O site hospedado continua sendo estático e não recebe essas notas em um banco compartilhado.

## Alternativa: servidor no seu computador

O site público funciona sem instalação. Use o servidor local quando quiser manter uma pasta no computador e gravar o acompanhamento automaticamente em arquivo.

1. Clone este repositório ou baixe **Code → Download ZIP** e extraia o pacote inteiro para uma pasta de sua escolha.
2. Tenha **Node.js 20 ou mais recente** instalado. Não é necessário instalar dependências npm.
3. No terminal aberto na pasta do projeto, execute `node server.mjs` ou `npm start`.
4. Abra **http://127.0.0.1:8080** no navegador.
5. Coloque os próximos arquivos `.json` em **`dist/dados/`**. Subpastas também são lidas.
6. Clique em **Atualizar** na página. Cada atualização relê a pasta e encontra arquivos novos, alterados ou removidos, sem reiniciar o servidor. A opção de atualização a cada 30 segundos pode fazer essa releitura enquanto a página estiver aberta.

No Windows, também é possível abrir `iniciar-windows.bat`. No macOS/Linux, execute `sh iniciar-mac-linux.sh`. Mantenha o terminal aberto enquanto usa a página; encerre com `Ctrl+C`.

Se a porta estiver ocupada:

```sh
node server.mjs --port 8081
```

O servidor escuta apenas no computador local por padrão (`127.0.0.1`). `--host`, `--port`, `HOST` e `PORT` permitem configurar a execução quando necessário. O comando `npm run dev` escuta em `0.0.0.0` para a infraestrutura de pré-visualização; para uso pessoal, prefira `npm start`.

## Três formas de usar

| Modo | Como abre | Como recebe novas pesquisas |
|---|---|---|
| **Servidor local** | `node server.mjs`, depois `http://127.0.0.1:8080` | Relê todos os JSON de `dist/dados/` a cada atualização. É o modo indicado para uma pasta fixa. |
| **HTML autônomo** | Gere com `node scripts/build-standalone.mjs` e abra `parcerias.html` | Inclui os JSON presentes na pasta no momento da geração. Use o seletor de pasta ou arquivos para ler novos JSON locais. |
| **GitHub Pages** | Abra o endereço público | Cada commit em `main` reconstrói o catálogo de `dist/dados/`. Clique em **Atualizar** depois de concluída a publicação. |

O manifesto é usado apenas pela versão estática hospedada e fica fora da pasta de dados. Ele não precisa ser editado para adicionar uma pesquisa. A seleção de arquivos locais no navegador permanece local e não publica esses arquivos no GitHub.

### Seleção de pasta no navegador

O arquivo `parcerias.html` inclui o HTML, estilos, scripts e os dados iniciais. Nesse modo, selecione os arquivos JSON autorizados para a consulta. O navegador não pode ler silenciosamente um caminho arbitrário do computador: a pasta precisa ser escolhida por uma pessoa.

Quando `showDirectoryPicker` está disponível, a página pode reler a pasta autorizada. Em navegadores que usam a seleção convencional de pasta/arquivos, pode ser necessário selecionar a pasta novamente para incluir arquivos que foram adicionados depois. Para atualização automática de uma pasta fixa, use o servidor local acima.

Ao usar **Somar à base carregada** e escolher outra pasta, os arquivos da pasta anterior permanecem como uma cópia da última leitura. Somente a pasta escolhida por último fica conectada para releitura; selecione as anteriores novamente para atualizá-las. A opção **Usar somente a seleção** substitui a base desta sessão.

## Adicionar uma nova pesquisa

O formato padrão é **JSON UTF-8**. Use a mesma estrutura do arquivo inicial:

```json
{
  "consultation_date": "2026-11-02",
  "projects": [
    {
      "name": "Nome do empreendimento",
      "developer": "Incorporadora",
      "city": "São Paulo",
      "neighborhood": "Bairro",
      "zone": "Sul",
      "address": "Rua e número",
      "project_url": "https://incorporadora.example/empreendimento",
      "stage": "Pré-lançamento",
      "launch_date": "Não publicada",
      "mcmv": "A confirmar",
      "mcmv_category": "a_confirmar",
      "partner_id": "P01",
      "checked_at": "2026-11-02",
      "source_urls": ["https://incorporadora.example/empreendimento"]
    }
  ],
  "partners": [
    {
      "id": "P01",
      "developer": "Incorporadora",
      "pf_url": "https://incorporadora.example/parcerias/pf",
      "pj_url": "https://incorporadora.example/parcerias/pj",
      "contact": "Contato profissional publicado",
      "commission_pf": "Não publicada",
      "commission_pj": "Não publicada"
    }
  ]
}
```

Há um modelo mais completo em **`exemplos/novo-lote.exemplo.json`**. Ele contém dados fictícios e está fora de `dist/dados/`, para não aparecer na pesquisa. Copie-o, substitua os exemplos pelos dados reais e somente então salve a nova pesquisa em `dist/dados/`.

### Campos que ajudam a consolidação

- `name`, `developer`, `city`, `address` e `project_url`: mantenha nomes e endereços completos, incluindo fase, torre ou condomínio quando isso identifica um produto independente.
- `checked_at`: data real da conferência do registro, preferencialmente `AAAA-MM-DD`.
- `consultation_date`: data geral da pesquisa, usada quando o registro não informa uma data própria.
- `source_urls` e `partnership_source_urls`: evidências do produto e do caminho de parceria.
- `partner_id`: referência a uma entrada de `partners` **no mesmo arquivo**. Um `P01` em outro lote não é automaticamente a mesma empresa.
- `partner_ids`: lista opcional de rotas adicionais, também resolvidas no mesmo arquivo. Permite um único empreendimento com credenciamento pela incorporadora e por uma intermediadora.
- `property_type`: tipo do empreendimento, como `Apartamento`, `Loteamento` ou `Casas e townhouses`.
- `launch_year`: ano confirmado, como `2025`, ou `null` quando não confirmado. Se presente, prevalece no filtro de ano; isso evita tratar o ano de um RI ou de uma notícia de anúncio como lançamento. Arquivos antigos sem esse campo continuam usando `launch_date`.
- `id`: identificador de origem, preservado para rastreabilidade. Repetir `E001` em outro arquivo não comprova que é o mesmo empreendimento.

### MCMV

Mantenha a categoria explícita quando conhecida:

| Valor de `mcmv_category` | Significado |
|---|---|
| `sim_fonte_oficial` | Menção nominal em fonte oficial ou release. |
| `sim_fonte_comercial` | Menção nominal em fonte comercial, pendente de confirmação com a incorporadora. |
| `nao_inferencia_preco` | Inferência por preço para as tipologias consultadas. |
| `a_confirmar` | Evidência insuficiente ou pendência de confirmação. |

Descreva a justificativa em `mcmv_evidence`. HIS, HMP ou financiamento Caixa isoladamente não foram convertidos em comprovação de MCMV nesta pesquisa. Datas de RI devem continuar identificadas como registro de incorporação, sem virarem automaticamente datas de lançamento.

## Registros repetidos e divergências

O explorador consolida cópias reconhecidas por informações do próprio empreendimento, preservando as origens. IDs locais como `E001` e `P01` não são tratados como identificadores universais.

Quando há versões de um mesmo empreendimento, a data de conferência ajuda a escolher os dados atuais; campos complementares e fontes são preservados. Informações conflitantes ficam indicadas para revisão. Nomes parecidos ou fases diferentes não devem ser fundidos apenas pela semelhança do texto.

A exportação JSON inclui o histórico das versões, rotas alternativas e proveniências. Reimportar esse JSON preserva essas informações; importar a exportação junto com os arquivos originais não conta as mesmas versões duas vezes. O CSV exporta o recorte para uso em planilhas, mas não é um formato de entrada.

O resultado da consulta é uma visão consolidada. **Os arquivos de pesquisa em `dist/dados/` não são reescritos, apagados ou alterados pela aplicação.** A gravação de status e notas usa o arquivo de acompanhamento separado. Para corrigir a base de pesquisa permanente, ajuste o JSON de origem ou acrescente uma nova pesquisa com data e evidência.

## Leitura da pasta e limites

- Apenas arquivos com extensão `.json` são importados; maiúsculas/minúsculas são aceitas.
- A leitura inclui subpastas, com limite de 20 níveis e 2.000 arquivos JSON por atualização.
- Limites de leitura: **10 MB por arquivo e 50 MB por atualização**.
- Um JSON inválido gera aviso individual e não impede a leitura dos outros arquivos válidos.
- Links simbólicos não são seguidos.
- A API de pesquisas é somente de leitura. A API de acompanhamento permite gravar apenas o arquivo de status/notas; não tem operação de envio de mensagens ou cadastro de parceria.
- Os dados locais são processados pela página; o servidor deste pacote não os encaminha a serviços externos. Abrir um link de incorporadora ou parceria navega para o respectivo site.

## Contrato da API local

`GET /api/datasets` retorna:

```json
{
  "mode": "server-folder",
  "folder": "dados/",
  "files": [
    {
      "fileName": "2026-11/novo-lote.json",
      "payload": { "projects": [], "partners": [] },
      "lastModified": 1793664000000
    }
  ],
  "errors": [
    { "fileName": "arquivo-invalido.json", "message": "JSON inválido. Corrija a sintaxe e clique em Atualizar." }
  ]
}
```

`fileName` é relativo a `dist/dados/`. `lastModified` usa milissegundos desde a época Unix, como `File.lastModified` no navegador. `payload` é o JSON original. O módulo de dados da página faz a normalização, resolução de parcerias, deduplicação e filtros.

### Acompanhamento local

`GET /api/tracking` devolve o envelope `dyhouse-partnership-tracking/v1`, com `revision` e `records`. `PUT /api/tracking` recebe o envelope completo, no mesmo formato. O servidor grava somente se a revisão enviada ainda for atual e incrementa a revisão; conflito retorna `409` com a versão atual para conciliação pela página. A gravação usa arquivo temporário e substituição atômica, mantendo o conteúdo anterior em `.bak`.

O servidor valida formato, status, datas e limite de 10 MB. Conteúdo inválido ou arquivo anterior ilegível gera erro e não é substituído silenciosamente. A escrita exige requisição JSON da mesma origem. Não coloque arquivos de acompanhamento em `dist/dados/`: essa pasta é destinada às pesquisas.
